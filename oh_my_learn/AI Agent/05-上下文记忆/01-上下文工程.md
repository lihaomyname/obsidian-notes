# 上下文工程

> 上下文工程管理模型在当前调用中能看到的指令、历史、记忆、检索结果、工具和输出要求，目标是在正确时间提供足够而不过量的信息。

## 上下文窗口的性质

Wayland 的链接把上下文窗口类比为 RAM：

- **有限**：内容最终会达到窗口和预算上限。
- **易失**：单次会话结束后不会天然跨会话保留。
- **昂贵**：输入越长，延迟和费用通常越高。

更大的窗口不代表可以无差别塞入更多内容。无关历史和冗长工具结果会稀释关键信息。

## 上下文包含什么

- 系统指令与行为边界
- 用户当前目标
- 对话和执行历史
- 长期记忆召回结果
- RAG 或文件检索结果
- 可用工具的 Schema
- 输出格式和验收要求

上下文工程比单纯修改 Prompt 更宽：Prompt Engineering 主要关注“怎么说”，上下文工程关注整个系统“让模型看到什么”。

## 四类策略

### Write：写到窗口之外

把计划、关键发现、待办和大段原始结果写入文件或外部存储，需要时再读回。Scratchpad、任务清单和项目说明文件都属于这一类。

### Select：按需选择

核心信息预加载，详细文件、历史记录和知识通过搜索或 RAG 在需要时取回。渐进式披露的原则是先提供索引和线索，再读取具体内容。

### Compress：压缩历史

用摘要替换冗长中间历史，同时保留初始目标、关键决策、未解决问题和最近对话。压缩是有损的，应保留 URL、文件路径等可恢复线索。

### Isolate：隔离子任务

把会产生大量中间信息的子任务交给独立上下文，只返回精炼结果。子 Agent 是一种隔离方式，但不是唯一方式。

## 与 RAG 的关系

RAG 主要解决“检索哪些外部知识”；上下文工程还管理指令、历史、工具、状态、预算、压缩和隔离。RAG 是 Select 策略中的一部分，不等于完整上下文工程。

## 一次调用的组装顺序

```text
不可覆盖的系统规则
  → 当前用户目标与验收条件
  → 当前状态、计划和未解决问题
  → 按任务召回的记忆与资料
  → 最近几轮原始对话
  → 可用工具 Schema
  → 输出格式
```

顺序本身不是唯一标准，重要的是明确优先级、来源和预算，避免旧摘要覆盖用户最新要求。

```python
def build_context(state, budget):
    blocks = []
    blocks += must_keep(state.system_rules)       # 最高优先级，不参与普通裁剪
    blocks += must_keep(state.current_goal)
    blocks += fit(state.plan, budget.plan)
    blocks += retrieve_relevant(state.query, budget.retrieval)
    blocks += take_recent(state.messages, budget.recency)
    blocks += select_tools(state.allowed_tools, budget.tools)
    return blocks
```

这里的 `fit`、`retrieve_relevant` 等是职责示意。生产实现还应给每个块记录来源、时间、作用域和估算 Token，便于排查“为什么模型看到了这段内容”。

## Token 预算不是平均切分

```python
budget = {
    "system_and_goal": 0.20,
    "working_state": 0.20,
    "retrieval": 0.25,
    "recent_messages": 0.20,
    "tool_schemas": 0.10,
    "output_reserve": 0.05,
}
```

比例是示意，不是固定最佳值。工具很多时应先过滤工具，而不是无限压缩用户目标；代码任务和资料问答的预算结构也会不同。

## 可恢复的压缩

一个好的历史摘要至少保存：

- 初始目标与用户后续修正；
- 已完成事项及证据；
- 未完成事项和阻塞原因；
- 关键决策及其依据；
- 文件路径、URL、工具调用 ID 等恢复线索；
- 最近错误，尤其是尚未解决的错误。

```python
def compact(history):
    old, recent = split_keep_recent(history, turns=6)
    summary = summarize(old, fields=[
        "goal", "constraints", "decisions", "completed",
        "pending", "errors", "recoverable_references",
    ])
    return [summary, *recent]
```

只保留“结论”可能让模型无法验证结论；因此大段工具结果可放入文件，摘要中保留文件路径和关键行号。

## RAG 的典型局限

- 切块可能把前提与结论拆开。
- 仅按相似度召回会遗漏精确编号或关系约束。
- 召回内容过多会占用窗口并引入冲突。
- RAG 不保存当前执行到哪一步，也不负责工具权限。

所以资料检索通常要与关键词过滤、元数据约束、状态存储和上下文预算一起使用。

## 课程资料中的 VFS

课程资料特别提到虚拟文件系统。结合链接内容，可把它理解为一个受控的上下文外存储层：Agent 通过文件接口写入、搜索和读取资料，以路径组织内容，并由 Backend 或沙箱决定这些路径映射到本地文件、状态存储还是远程 Store。

```text
/workspace/plan.md          当前计划
/workspace/findings.md      已验证发现
/artifacts/tool-output.json 大型工具结果
/memory/project.md          跨会话项目约定
```

路径让模型能先列目录、搜索，再读取小片段。VFS 的 Backend 可以映射到本地磁盘、线程状态或远程对象存储，但访问权限必须保持一致，不能因更换 Backend 而意外扩大作用域。
