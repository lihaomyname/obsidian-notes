# 多轮对话与状态机

> 多轮 Agent 需要把消息、任务状态、下一步节点和中断信息持久化，使执行能够分支、暂停、恢复、回滚和等待人工决策。

## 为什么不只保存聊天记录

复杂 Agent 的状态不只有 messages，还可能包含：

- 当前目标和计划
- 已完成、待执行和失败步骤
- 工具调用及结果
- Token 与费用预算
- 用户、项目和权限作用域
- 待审批动作与恢复位置

只保存聊天文本无法可靠恢复这些执行状态。

## 图与状态机

课程资料提出使用 Graph 管理复杂状态流转。可以把节点理解为模型调用、工具执行、校验或人工审批，把边理解为固定或条件转移。

```text
接收请求 → 模型决策 → 是否调用工具？
                       ├─ 是 → 工具执行 → 回到模型决策
                       └─ 否 → 验收 → 输出
```

循环必须有终止条件，条件分支必须有无法匹配时的兜底路径。

## 状态 Schema 示例

```python
from typing import TypedDict, Literal

class AgentState(TypedDict):
    thread_id: str
    messages: list[dict]
    goal: str
    plan: list[str]
    current_step: int
    status: Literal["running", "waiting", "failed", "done"]
    tool_calls: list[dict]
    pending_approval: dict | None
    retry_count: int
    budget_remaining: int
    last_error: str | None
```

消息只是状态的一部分。Schema 能让节点明确读写哪些字段，也便于检查点序列化和迁移。

## 节点与条件边

```python
def decide_next(state: AgentState) -> str:
    if state["budget_remaining"] <= 0:
        return "fail_budget"
    if state["pending_approval"]:
        return "wait_human"
    if state["last_error"] and state["retry_count"] >= 2:
        return "fail_retry_limit"
    if goal_is_satisfied(state):
        return "finish"
    if model_requested_tool(state):
        return "execute_tool"
    return "reason"
```

每个循环都应有预算、重试上限或目标验收等终止条件；`else` 兜底分支要进入可诊断的失败状态，不能静默卡住。

## Checkpoint 里应保存什么

- 完整业务状态及 Schema 版本；
- 当前节点和下一条边；
- 已完成工具调用的 ID 与结果摘要；
- 待审批动作及原始参数；
- 线程 ID、检查点 ID 和父检查点；
- 时间、错误与重试计数。

```python
checkpoint = {
    "schema_version": 2,
    "thread_id": state["thread_id"],
    "node": "before_send_email",
    "state": state,
    "completed_effects": ["tool-call-17"],
}
save_checkpoint(checkpoint)
```

`completed_effects` 可辅助恢复时去重，但真正的外部副作用仍应由工具通过幂等键保证。

## Checkpoint 与线程

检查点保存某一线程在特定时刻的完整状态。恢复执行时必须定位到同一个线程和检查点，否则系统不知道从哪个状态继续。

Checkpoint 支持：

- 多轮对话连续性
- 失败后的重试或回滚
- 长任务暂停后继续
- Human-in-the-Loop 审批
- 调试时查看执行停在哪里

## Human-in-the-Loop

Deep Agents 链接将人工决策区分为：

| 决策 | 含义 |
| --- | --- |
| approve | 按原参数执行 |
| edit | 修改参数后执行 |
| reject | 不执行，并把原因反馈给 Agent |
| respond | 人类直接提供工具结果，适合询问用户类工具 |

删除、发送、部署等副作用工具应使用 approve/edit/reject；`respond` 不应被当作软拒绝，因为模型可能把它理解为工具已经成功完成。

## 中断与恢复流程

1. Agent 运行到敏感动作。
2. Runtime 保存线程状态并返回中断信息。
3. 用户查看工具名称、参数和影响范围。
4. 用户批准、修改或拒绝。
5. 使用相同线程标识恢复执行。

没有持久化 Checkpointer，中断后就缺少可靠恢复基础。

```python
def execute_sensitive_call(state, call):
    if call.risk == "high" and not call.approved:
        state["pending_approval"] = {
            "tool": call.name,
            "arguments": call.arguments,
            "reason": call.risk_reason,
        }
        save_checkpoint(state)
        return Interrupt(state["pending_approval"])

    # 使用稳定调用 ID，恢复后重复到达也不会重复产生副作用
    return tool_gateway.execute(call, idempotency_key=call.id)
```

恢复必须沿用同一 `thread_id`。如果用户选择 edit，应把修改后的参数作为新的审计记录保存，不能覆盖原始提议而失去变更痕迹。

## 回滚、重试与补偿

- **回滚状态**：把 Agent 的内部状态恢复到旧检查点。
- **重试节点**：再次执行失败的计算或只读调用。
- **补偿动作**：对已发生的外部副作用执行反向业务操作。

三者不能混为一谈。恢复数据库里的 Agent 状态并不会自动撤回已经发出的邮件；若外部系统不支持事务回滚，就需要显式补偿或人工处理。

## 多分支会话

从旧检查点尝试另一方案时，应创建带父检查点的新分支，而不是覆盖原历史：

```text
checkpoint-10
├── branch-A：继续原计划 → failed
└── branch-B：修改参数   → completed
```

这种结构便于审计和比较，但最终只能让一个分支提交不可重复的外部副作用，避免“双写”。

## 风险分层

- 低风险只读操作通常自动执行。
- 写入和外部 API 可按场景审批。
- 删除、发布、发信、生产 SQL 等高风险操作必须严格审批。
- 即便是只读操作，访问密钥和隐私路径也不能自动放行。
