# 沙箱与执行安全

> 当 Agent 能编辑文件、运行 Shell 或执行代码时，必须把不可信执行限制在明确的文件、进程、网络和资源边界内。

## 为什么需要沙箱

Agent 生成的命令可能错误，用户输入和外部文档也可能诱导模型执行危险动作。仅在提示词中写“不要做危险操作”不足以形成安全边界，限制必须由 Runtime 或操作系统层强制执行。

## 需要控制的边界

- **文件系统**：允许路径、只读路径、禁止访问的密钥目录。
- **进程**：允许的命令、子进程数量、执行超时。
- **资源**：CPU、内存、磁盘和输出大小。
- **网络**：是否允许联网、允许访问的域名与端口。
- **身份与凭据**：最小权限、短期凭据和租户隔离。

课程资料把 WASI 和 Docker 作为可选隔离技术。二者是实现手段，不代表只要放进容器就自动安全；仍需正确配置挂载、网络、权限和资源限制。

## 分层防护

```text
工具白名单与参数 Schema
          ↓
策略判断与人工审批
          ↓
沙箱或容器隔离
          ↓
超时、资源限制与输出截断
          ↓
日志、审计与异常终止
```

## 先定义威胁模型

至少考虑四类输入：模型可能生成错误命令；用户可能明确请求危险操作；网页和文档可能包含提示注入；工具返回可能伪装成高优先级指令。对应的资产包括工作区文件、凭据、内部网络、生产系统和用户数据。

因此控制面与执行面最好分开：

```text
控制面：解析意图 → 校验策略 → 判断审批 → 签发一次性执行许可
执行面：在受限环境执行 → 限制资源 → 收集结果 → 销毁环境
```

执行面不能因为命令文本声称“已获授权”就自行放宽限制。

## 策略对象示例

```python
from dataclasses import dataclass

@dataclass
class ExecutionPolicy:
    writable_roots: tuple[str, ...]
    readable_roots: tuple[str, ...]
    allowed_commands: frozenset[str]
    network_domains: frozenset[str]
    timeout_seconds: int
    max_output_bytes: int
    memory_mb: int
    require_approval_for: frozenset[str]

POLICY = ExecutionPolicy(
    writable_roots=("/workspace",),
    readable_roots=("/workspace", "/opt/reference"),
    allowed_commands=frozenset({"python", "pytest", "rg"}),
    network_domains=frozenset(),             # 默认禁止联网
    timeout_seconds=60,
    max_output_bytes=1_000_000,
    memory_mb=512,
    require_approval_for=frozenset({"delete", "publish", "send"}),
)
```

这只是策略模型；普通 `subprocess` 的超时参数不能提供完整文件、网络和内核隔离，真正的边界必须由容器、WASI、操作系统权限或远程沙箱落实。

## 执行前检查

```python
def authorize(action, policy):
    target = resolve_and_normalize(action.target)

    # 必须先解析真实路径，防止 ../ 和符号链接越界
    if action.kind == "write" and not under_any(target, policy.writable_roots):
        return Deny("目标不在可写目录")

    if action.command not in policy.allowed_commands:
        return Deny("命令不在白名单")

    if action.risk in policy.require_approval_for:
        return InterruptForApproval(action)

    return Allow()
```

参数级检查不能只匹配字符串前缀；路径要规范化，URL 要解析 Host，Shell 最好以参数数组执行而不是拼接字符串。

## WASI、容器与远程沙箱

| 方案 | 适合场景 | 仍需关注 |
| --- | --- | --- |
| WASI / WebAssembly | 运行可编译为 WASM 的受限程序 | 系统接口、宿主能力授予、兼容性 |
| Docker / 容器 | 需要常见 Linux 工具链和依赖 | 挂载、用户权限、网络、资源上限 |
| 远程临时沙箱 | 多租户、弹性任务、执行后销毁 | 身份、上传数据、日志和租户隔离 |

容器不是天然安全边界：使用 root、挂载宿主敏感目录、开放 Docker Socket 或无限制联网都会削弱隔离。

## 执行后的处理

- 限制 stdout/stderr 大小，大结果保存为文件并返回摘要。
- 记录策略版本、调用者、参数摘要、审批人和退出状态。
- 将工具输出按不可信数据处理，不能把输出中的指令提升为系统命令。
- 对临时凭据、容器和工作目录做生命周期清理。
- 写操作使用幂等键或事务边界，避免恢复执行时重复产生副作用。

## 危险操作

- 递归删除、覆盖大范围目录
- 写入工作区外路径
- 修改生产配置或部署
- 访问私钥、令牌和用户隐私数据
- 任意网络请求或数据外传

高风险操作应在执行前展示目标和参数，允许用户批准、修改或拒绝。只读操作通常风险较低，但读取敏感路径仍需授权。

## 沙箱与 HITL 的边界

沙箱限制“即使执行也不能越界”；Human-in-the-Loop 决定“是否允许执行这一次动作”。二者互补，审批不能替代隔离，隔离也不能替代业务授权。
