# 智能体经典范式

> 智能体范式规定了模型如何组织“理解目标、推理、行动、检查和改进”。ReAct、Plan-and-Solve、Reflection 分别侧重环境适应、全局规划和结果优化，三者不是互斥框架，而是可以组合的控制循环。

## 一、为什么需要范式

LLM 能生成文本和进行推理，但要成为 Agent，还需要解决三个问题：

1. **如何连接外部世界**：什么时候搜索、计算、读文件或调用 API？
2. **如何完成复杂任务**：怎样拆解步骤并在执行过程中保持目标一致？
3. **如何提升初次结果**：怎样发现事实、逻辑、效率或遗漏问题并改进？

经典范式就是对这些问题的不同回答：

```text
ReAct             边观察边行动：下一步做什么？
Plan-and-Solve    先规划后执行：完整路径是什么？
Reflection        先产出再改进：结果还能怎样变好？
```

## 二、三种范式对比

| 范式 | 核心循环 | 最擅长解决 | 主要优势 | 主要代价 |
| --- | --- | --- | --- | --- |
| [[02-ReAct循环\|ReAct]] | 思考 → 行动 → 观察 | 外部信息未知、过程需要动态调整 | 适应环境、实时纠错、工具协同 | 串行调用较多，可能局部最优或循环 |
| [[03-Plan-and-Solve\|Plan-and-Solve]] | 规划 → 逐步执行 | 路径可分解、依赖关系清晰的复杂任务 | 结构清晰、目标稳定、便于跟踪 | 初始计划错误会向后传播，环境变化时不灵活 |
| [[04-Reflection\|Reflection]] | 执行 → 反思 → 优化 | 对质量、准确性或性能要求高的产物 | 能修复遗漏并阶梯式提升质量 | 每轮至少增加反思与优化调用，延迟和成本高 |

## 三、快速选择

### 选择 ReAct

适合：

- 需要搜索实时信息、调用 API 或读取系统状态
- 下一步依赖工具刚刚返回的结果
- 探索性排障，事先无法列出完整路径

例子：调研最新产品价格、定位线上 500 错误、跨多个页面查证事实。

### 选择 Plan-and-Solve

适合：

- 任务可以稳定地分解成有先后关系的步骤
- 需要保持全局结构和进度
- 中间环境变化较少

例子：数学应用题、结构化报告、代码模块设计、迁移方案执行。

### 选择 Reflection

适合：

- 初稿容易评价，且存在明确质量标准
- 错误代价较高，值得用更多成本换质量
- 实时性要求不高

例子：关键代码、技术报告、研究分析、算法优化。

## 四、组合使用

实际系统通常不会只使用一种范式。

### Plan-and-Solve + ReAct

先制定全局计划，每个步骤内部再用 ReAct 获取外部信息：

```text
规划任务
  ├─ 步骤 1 → ReAct 搜索与验证
  ├─ 步骤 2 → ReAct 调用 API
  └─ 步骤 3 → 汇总结果
```

它兼顾全局方向和局部适应性，适合调研、开发和多阶段工作流。

### ReAct + Reflection

ReAct 先完成有证据的初稿，Reflection 再检查事实、逻辑、遗漏和表达质量。适合答案必须可靠但获取信息过程又不可预知的任务。

### Plan-and-Solve + Reflection

执行计划后，由 Reflection 检查计划覆盖度和最终产物。如果发现根本性问题，应允许回到规划阶段，而不只是润色最后答案。

### 三者组合

```text
Plan：生成可追踪的任务计划
  ↓
ReAct：逐步执行，依据环境反馈动态调整
  ↓
Reflection：按验收标准审查并优化最终结果
```

这是更接近生产级 Agent 的形态，但必须同时设置预算、超时、最大轮数和人工确认点。

## 五、统一的工程骨架

```python
def run_agent(task, config):
    # Plan：先生成全局计划，避免执行过程失去整体方向。
    plan = planner.create_plan(task)

    # 统一保存任务、计划和各步骤结果，供后续步骤共享上下文。
    state = {"task": task, "plan": plan, "results": []}

    for step in plan:
        # ReAct：每个计划步骤内部仍可根据工具反馈动态调整。
        result = react_executor.run(
            goal=step,
            context=state,
            max_iterations=config.react_iterations,
        )
        state["results"].append(result)

        # 如果环境反馈推翻了原计划，交回规划器重新规划。
        if result.requires_replan:
            plan = planner.revise_plan(state)

    # 将所有步骤结果合成为可评审的初稿。
    draft = synthesize(state)

    for _ in range(config.reflection_iterations):
        # Reflection：依据明确的验收标准审查，而不是笼统润色。
        feedback = reviewer.review(task, draft, config.acceptance_criteria)
        if feedback.passed:
            break

        # 只在未通过验收时生成修订稿。
        draft = refiner.improve(task, draft, feedback)

    return draft
```

这个骨架表达的是控制关系，不是可直接运行的完整框架。生产实现还需要工具权限、持久状态、异常恢复、日志、预算和质量验收。

## 六、设计时的共同原则

- **结构化状态**：计划、动作、观察、反馈尽量使用明确的数据结构。
- **证据优先**：模型声称完成不等于任务完成，要检查必要工具和验收条件。
- **有界循环**：所有循环都有最大次数、预算和超时。
- **失败可见**：保留原始模型输出、工具错误和停止原因。
- **上下文节制**：只携带当前步骤需要的信息，旧历史应摘要或外置。
- **允许升级策略**：ReAct 卡住时重新规划；执行完成但质量不足时进入 Reflection。

## 七、一句话记忆

- **ReAct**：边做边想，擅长应对未知环境。
- **Plan-and-Solve**：先想清楚再做，擅长稳定的多步骤任务。
- **Reflection**：做完再审，擅长用额外成本换取更高质量。
